
==============================================================================
(A) THE SPLIT BELONGS TO THE TOKENIZER, NOT THE WORD
==============================================================================
  cl100k_base  vocab=100277   str | aw | berry
               496  675  15717
  o200k_base   vocab=200019   st | raw | berry
               302  1618  19772

  Same 10 characters. Different cut. 'str|aw' vs 'st|raw'.
  The boundary is an artifact of which merge table was trained,
  not of anything inside the word.

==============================================================================
(B) CONTROL -- SPACING THE WORD CHANGES THE INPUT ENTIRELY
==============================================================================
  plain   'strawberry'          ->  3 tokens
          pieces: ['str', 'aw', 'berry']
          ids   : [496, 675, 15717]
  spaced  's t r a w b e r r y' -> 10 tokens
          pieces: ['s', ' t', ' r', ' a', ' w', ' b', ' e', ' r', ' r', ' y']
          ids   : [82, 259, 436, 264, 289, 293, 384, 436, 436, 379]

  3 tokens vs 10 tokens for the same word.
  Spaced out, every letter gets its OWN id -- so 'r' becomes
  countable the same way any repeated token is countable.
  The prompt trick does not make the model smarter about letters.
  It changes the input so the letters are tokens in the first place.

==============================================================================
(C) THE EMBEDDING LOOKUP IS A ROW INDEX, NOT A SPELLING
==============================================================================
  ILLUSTRATION (constructed): a real embedding table is not public,
  so the vectors below are random, seed=7375, d_model=8.
  What is NOT constructed is the operation: E[token_id] -> row.

  E[496   ]  ('str' )  ->  [-0.64  -0.134  0.148  1.137 -0.314  0.107  0.41   0.264]
  E[675   ]  ('aw'  )  ->  [ 0.41  -0.665 -0.324 -1.789 -0.678 -0.266  0.002 -0.709]
  E[15717 ]  ('berry')  ->  [ 1.679  0.606 -1.211  0.848  1.029  0.478 -1.293  0.234]

  Nothing on the right-hand side is addressed by character.
  There is no slot for 'the 3rd letter'. The row is fetched by the
  integer and by nothing else. The spelling was consumed upstream.

==============================================================================
(D) THE MERGE TABLE FOLLOWS FREQUENCY, NOT SPELLING
==============================================================================
  string         chars  toks ch/tok  pieces
  the                3     1   3.00  ['the']
  people             6     1   6.00  ['people']
  berry              5     1   5.00  ['berry']
  strawberry        10     3   3.33  ['str', 'aw', 'berry']
  zyzzyva            7     4   1.75  ['zy', 'z', 'zy', 'va']

  'berry' alone is ONE token (15717). Inside 'strawberry' it is still
  that same token -- but 'straw' is not common enough to survive, so
  it breaks into 'str'+'aw'. Meanwhile 'zyzzyva' (7 chars) shatters
  into 4 tokens. BPE merges the most frequent adjacent pairs during
  training; nothing in that process is aware of letters or spelling.
