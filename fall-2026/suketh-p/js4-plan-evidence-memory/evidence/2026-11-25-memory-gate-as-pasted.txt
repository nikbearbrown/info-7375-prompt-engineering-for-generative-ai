A. The record
1. What every remembered fact holds
- board · The ATS and board slug, such as greenhouse/anthropic.
- posting_key · The board’s posting identifier. I’ll use the Greenhouse id or the Ashby jobUrl as stored text.
- fact_type · The observation I’m keeping, such as first seen, listed, missing from the list, or closed.
- value · What the source supports about that posting at the time of observation.
- captured_at · When the source captured the observation. A replay keeps the original capture time.
- capture_run_id · The run that saved the underlying response.
- recorded_by_run_id · The run that committed the fact to memory.
- source_kind · Whether the evidence comes from a saved capture, a seeded fixture, or a legacy import.
- source_path · The approved relative path to the saved response or fixture.
- source_sha256 · The digest that identifies the exact source bytes the check used.
- source_locator · The posting key and field to inspect, or the full board key set if the claim is about absence.
- verification_ref · The check result that links the fact back to its source.
Watcher notes stay proposals until the coordinator validates them. Posting text stays literal data throughout the handoff.

2. What memory may say about whether a posting is still open
Statement	Evidence I require
Listed as of the capture time	The exact board and posting key appear in a usable saved response whose hash and key set pass verification.
Missing from this list. Status unknown.	The exact key is absent from a later usable response for the same board. Keep its first-seen record and last confirmed listing.
Closed in the seeded fixture as of the stated time	A later, explicitly labeled closure fixture names the same board and key. A real-world closure claim would need a separately approved source that explicitly establishes it.
I cannot tell	The board failed, the response is unusable, the evidence conflicts, or the available observation is too old to answer a present-tense question. A failed check leaves the last verified observation in history.


If the key returns on the same board, record the new listing observation and keep its original first-seen record.

B. The revision boundary
3. What one revision covers
One revision covers the entire jobwatch-state/3 file in the replay workspace, including all boards, seen keys, remembered observations, source references, and committed runs. A decision about new postings can depend on several boards, so I want one consistent starting snapshot. The per-run watcher files and merged notes.json are evidence for the proposed update.

The replay starts at revision 0. The writer holds the lock while it rereads the file, compares the approved starting revision and SHA-256, and atomically replaces the state. A successful commit advances the revision once. A mismatch voids that run’s approval and preserves the current state.

4. Which decisions read which parts of memory
Decision	What it reads
Is this new?	The board’s full seen-key history and the current verified key set. A board’s first usable capture establishes its baseline.
What can I say about liveness?	The last verified observation and its timestamp, plus any later verified listing or explicit closure evidence for the same board and key.
What changed between the two days?	Both dated captures, their verified key sets, and the committed revisions that link them.
Can the watcher notes merge?	Both staged contributions, their board and source references, and the shared starting revision and hash.
Can state advance?	The full current state, the verified proposal, and my approval for the exact run ID, path, starting revision, and SHA-256.
