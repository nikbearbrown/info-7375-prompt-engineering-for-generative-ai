## 2. One change to one object at a time

The full method and results are in [`experiments/REPORT.md`](experiments/REPORT.md), generated by `python3 experiment.py report`.

- **Baseline:** FILTER.md v1.1, run `filter-v1.1-2026-11-18T212545Z`. Before measuring, `experiment.py flips` reproduced every field of every saved result in memory.
- **Candidates:** registered in `experiments/candidates.json` on 2026-11-24, after my 60 tuning labels were committed (`e926b963`) and before any held-out posting was drawn. Each candidate changes exactly one value, in memory. `apply_change` refuses to run if anything else would differ (`test_exactly_one_value_changes_and_the_original_is_untouched`). The real rules files are never written.
- **Held-out labels:** 20 postings I had not labeled, drawn from the postings each change flips (`audit/heldout-filter-v1.1-2026-11-18T212545Z/`), on a blind sheet. A posting a change does not flip cannot tell the two versions apart, so the flips are what has to be labeled.

| Change | Object | Flips (exact, all 2,418) | Tuning labels | Held-out labels |
|---|---|---:|---|---|
| X1: threshold 65 → 55 | a setting | 44, all rejected → review | 1 improved (row 39), 2 regressed (rows 4, 5) | 15 drawn of 41; **not labeled yet** |
| X2: a related title needs 2 topics, not 1 | the filter file (Rule 1) | 8, all review → rejected | 2 improved (rows 55, 60), 1 regressed (row 59) | all 5 remaining; **not labeled yet** |
| X3: treat "may also have" headings as preferred | the filter file (Rule 8) | 0 | none | none: it changes no decision |

The held-out measurement is not done until I label the 20 postings. Until then there is no held-out result, and no change is adopted. The decision log is [`experiments/RULE-CHANGE-LOG.md`](experiments/RULE-CHANGE-LOG.md).

## 3. What persistence is not proof of

A behavior that changes between sessions does not mean anything was trained. In this project, every change in behavior can be traced to a file:

- **The filter** changes only when `FILTER.md`, `rules/*.json` or the code changes. Each run records the sha256 of all three (`runs/*/summary.json`). If the same files give the same results, nothing "learned" anything, and `experiment.py flips` checks exactly that.
- **My labels** are saved in CSV files. Saving them makes them persist, but it trains nothing. They are used only to count, and to choose which changes to try.
- **Claude's behavior** in my sessions depends on what it is given: the prompt, the tools, and the files Claude Code loads at start-up. The real headless session reported an auto-memory folder for this repository in its start-up message, and Claude Code reads `CLAUDE.md` files. If Claude acts differently next week, a changed prompt, tool list, memory file, setting or model version can explain it. None of those is training on my data.
- **The tool server** has no memory between sessions. Each session starts fresh, and the transcripts are a record, not an input.
