# Job-Search Agent 2 — The Loop, the Tools, and the Diff

**Om Raut** · INFO 7375, Fall 2026 · Job-Search Agent 2 (Chapters 4–6) ·
GitHub folder: `fall-2026/om-r/js2-loop-tools-diff/`

This agent extends Job-Search Agent 1's single-board watch to three boards
across two ATS systems. It runs a bounded loop with four explicit exits and
three budgets. Every tool call goes through permissions enforced in code.
Its one non-trivial change, removal detection, was reviewed test-first in a
diff-review packet.

The spec is `GATE.md`, written before any code. Where it was amended later,
each amendment is dated, and one (2026-11-10) says plainly that it was
written after the code.

## Language and toolchain

- **Python 3.11** (tested on 3.11.15), **standard library only**. This was
  checked by parsing every import in `agent/`, `tests/` and `tools/` with
  `ast` and comparing against `sys.stdlib_module_names`. The modules used
  are `argparse`, `datetime`, `hashlib`, `importlib`, `io`, `json`,
  `logging`, `os`, `pathlib`, `re`, `shutil`, `socket`, `subprocess`,
  `sys`, `tempfile`, `time`, `traceback`, `unittest`, `urllib`. The only
  other imports are the project's own packages (`agent`, `tests`).
  Third-party packages: none.
- **No `requirements.txt`.** JS1 needed `anthropic==0.39.0` for its
  judgment step. JS2 has no judgment step, so nothing beyond JS1's standard
  library baseline was added, and the Anthropic SDK was dropped.
- **Network hosts:** `boards-api.greenhouse.io` and `api.lever.co`, HTTPS
  only, enforced in `agent/permissions.py`. `api.anthropic.com` was removed
  from the allow-list until judgment code exists (GATE.md, 2026-11-09
  amendment).
- **Tests:** `unittest`, 46 tests.

## What is and isn't committed

- `evidence/` holds the raw board responses, saved exactly as received.
  Every run writes a fresh set (about 15 MB per run across the three
  boards), so it is regenerated by any run and is **not committed**
  (`.gitignore`). The one exception is constructed fixtures named
  `*_SEEDED_*.json`: they are hand-built, labeled as not live data in both
  the filename and the content, cannot be regenerated by a run, and **are
  committed**.
- `state/` holds per-board seen-id state (`<board>_seen.json`). It is local
  run state and is **not committed**.
- `logs/` is **committed**. The numbered `NN_*.txt` and
  `review_packet_NN_*.txt` files are the test and run outputs in the order
  they were produced. `logs/run_*.json` is each run's own full JSON report
  and is the run record.

## What actually ran vs. what's proposed

Everything above actually ran, on 2026-11-09 and 2026-11-10 (UTC), and was
run again end to end in a fresh clone on 2026-11-10. The real output is in
`logs/`. Nothing in this submission is a `[TODO]` stub, and the loop,
permissions and tools are all in use.

Constructed input was used in exactly three places, each labeled in its
own file:

- **SEEDED empty Stripe response.**
  `evidence/stripe_SEEDED_empty_20261110T000450Z.json` is a hand-built
  `{"jobs": []}` with a `_SEEDED_NOTICE` field. It is used in
  FINISHED-WRONG-ANSWER.md.
- **SEEDED gitlab minus-one response.**
  `evidence/gitlab_SEEDED_minus_one_20261110T000619Z.json` is the real
  2026-11-09 gitlab response with posting `8858174002` dropped and
  `content` stripped. It has a `_SEEDED_NOTICE` field and is used in
  REVIEW-PACKET.md. All three real gitlab responses were byte-identical, so
  no live removal was available.
- **Reconstructed pre-fix retry-budget code.** The bug was fixed before
  `loop.py` was first committed, so the "reverted fix" in
  `logs/11_retry_budget_test_vs_reverted_fix.txt` was rebuilt from the
  patch applied at the time. The exact diff is in the log (FRICTIONAL.md,
  entry 1).

Also deliberately wrong, and labeled as such:

- `agent/wrong_stub_budget.py` and `agent/wrong_stub_failed_board.py` exist
  only so the wrong-version tests can be shown failing. The loop never
  imports them.
- The mutated `permissions.py` and the wrong removal patches are applied
  only to temporary copies, by `tests/mutation_check.py` and
  `tools/weak_patch_check.py`.

**Not checked**

- What happens if a posting disappears and reappears with the same id between two runs — both snapshots would still contain it, so no removal is ever flagged.
- An ATS reusing an id for a different posting, which would hide a real removal from an id-based comparison.
- Whether the loop can tell a broken board returning 200 OK with an empty list apart from a board that genuinely removed every posting — the seeded replay shows both look identical from inside the loop.
- Removal detection on Lever specifically, including string ids and results spread across multiple pages.
- Nothing structurally forces GATE.md to be updated before a behavior change ships. We only caught this gap because I happened to ask for a scope review that time.

**Not claiming**

The empty-Stripe replay and the removal demo both used seeded inputs. The deliberate 404 was live and tested how the loop handles an explicit board failure. The three real GitLab responses were byte-identical, so I never observed a live removal. The count-drift check is a separate script with a fixed cutoff (a drop of more than 50%, or to zero) — the loop itself can still report `finished` without it ever running. The removal tests came before the patch, but the removal rule went into GATE.md only after the code already existed. JS2 ends at fetching and reporting; it has no job-judgment step.
