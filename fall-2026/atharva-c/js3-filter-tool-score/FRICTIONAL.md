## Nov 23, 2026 — Day 1: data, FILTER.md, label sample (DRAFT)

The evidence rules need text to quote, so I chose to re-collect. Run `run-20261123-185425Z` (3 GET requests, 1.8 s, status `finished`) returned 400 postings: Robinhood 162, Affirm 218, Wealthfront 20. All 400 have title, location and text.
* **Decisions I made:** re-collect with `?content=true` instead of working on titles only. Keep Sam Rivera as a new-grad **software engineering** persona instead of switching to AI/ML. Drop JS2's deliberate 404 board.
* **What the survey showed before any rule existed:** 149 of 199 engineering-ish titles carry a seniority word. `Software Engineer II` at Affirm asks for "5+ years", so the title level is not trustworthy. `Full Stack` appears in analytics titles (`Analytics Lead, Full Stack`). Affirm posts one copy of a role per country (`Remote US` / `Remote Canada`), so 91 postings share a board and title with another posting. Each of these became a rule or a wrong version in FILTER.md v1.0.
* **Friction 1 — Claude broke FILTER.md and repaired it:** a one-word fix to wrong version W1 was done with a Python find-and-replace. The search string did not match (the file has backticks around the title), `find()` returned −1, and the script appended a second copy of the file to itself (230 lines, two changelogs). Claude caught it from the `grep` output, rebuilt the original from the first copy, checked it (115 lines, one changelog, ends at the changelog note), and then applied the fix. This happened before anything was committed.
* **Friction 2 — the first label sample could not measure anything:** the first seeded draw (60 postings: 40 from engineering-ish titles, 20 from the rest) had about **one** likely keep in its 30-posting held-out half. No change to the filter could show up on that. Nothing had been labeled yet, so the sampler was redesigned (v2): all 50 engineering titles without a seniority/intern word (A1), plus 20 random seniority titles (A2), plus 20 random others (B), 90 in total, split 45/45, seed 2026. **Cost, recorded in `agent/label_sheet.py`:** A1 reuses the G1/G2 word list, so the label set is not a random sample of the 400, and any rate on it is a rate on this stratified set.
* **What Claude did / what I accepted (my words):** Claude drafted FILTER.md v1.0 from the survey. I accepted it as written and had it committed unchanged before writing any filter code so the spec would stay cleanly separated from implementation. Specifically, the survey justified the structural choices right away: 149 of 199 engineering-ish titles had seniority words (G1), Affirm's `Software Engineer II, Backend` asked for 5+ years despite the title (R2 penalizing ≥ 4 years in the body rather than trusting title numerals), `Full Stack` appeared inside analytics titles like `Analytics Lead, Full Stack` (requiring full role phrases in R1), and 91 duplicate titles across country-specific postings meant filtering by location before deduplicating (G3 before grouping). What I am accepting on faith until we label the 90 rows and run the audit are the unmeasured numbers and two known leaks: the 0.50 cutoff, the +0.30 / −0.40 R2 weights, the fact that R2 + R3 alone (`0.30 + 0.20 = 0.50`) can pass a non-engineering title if it explicitly asks for entry level and ≤ 2 years, and the G3 fallback that lets unrecognized or empty locations pass instead of rejecting.

## Nov 23, 2026 (later) — Labels, and a survey fact that was wrong (DRAFT)

* **What happened:** I hand-labeled all 90 sampled postings: dev 6 keep / 39 reject, held-out 5 keep / 40 reject. Committed alone in `215f29a`, before any filter code. Claude wrote my pasted labels into the CSVs and checked every year count I cited in a reason against the posting text. All 29 matched, except one row whose reason I had guessed.
* **The label I changed:** `affirm:8032173003` (`Software Engineer II, Full Stack (Card Acquisition)`, Remote US). My first label was reject, "likely 2-5+ yrs". Claude pointed out that the posting says "1.5+ years", word for word the same as two other Affirm postings I had labeled keep. I changed it to keep, "unsure: SWE II asking 1.5+ yrs, US remote", before the labels were committed.
* **Survey fact was wrong:** while checking those labels, Claude found that its Day 1 survey misread "1.5+ years" as "5+ years". The regex took whole numbers only, so it picked up the "5" after the decimal point. That false "Software Engineer II asks for 5+ years" claim had gone into FILTER.md v1.0 (R2's reason, W2's example), into this log's first entry, and into my own accepted-text bullet. I accepted it because it was a vivid example, and I didn't open the posting. Re-checked across all 23 `Engineer II` titles (counted by script; a first hand count said 15 for the 1.5+ group, which a reviewer caught because the buckets summed to 22): 16 ask for 1.5+ years, 2 for 2+, 2 for 3+, 2 for no fixed minimum, and 1 gives no years.
* **What I changed:** FILTER.md v1.1, a documentation correction only. v1.0's text is left as committed, with a correction note at the top and a v1.1 changelog row. No rule changed. W2 gets a real example (`Software Engineer II, Backend (Test Infra)`, 3+ years, my label reject). The filter must read "1.5+" as 1.5, so that test comes first tomorrow.
* **What I learned:** a fact in the spec was produced by the same kind of regex the filter will use, with the same bug. The spec was only checked by reading the matched sentences, which caught it here.
* **Still open:** nothing has been run against the labels yet. Day 2 is to write the tests, then `agent/filter.py`, then the audit.
