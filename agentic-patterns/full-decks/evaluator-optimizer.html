Evaluator-optimizer

One call writes. A second call judges. Repeat.

This deck covers one pattern: the evaluator-optimizer workflow. It shows the shape of the loop, one real run of it, what each round costs, and the signs that say it will pay off.

The claim

One call writes and a second call judges, in a loop. It pays off when the criteria are clear and feedback makes the result better.

The first sentence is the shape. The second is the condition. Both come from Anthropic's article and its cookbook notebook: the workflow fits when there are clear evaluation criteria and when iterative refinement adds measurable value.

Part one

The shape

A generator, an evaluator, and feedback between them

Four slides: the loop, what travels back to the generator, one saved run from the notebook, and what the feedback changed in that run.

Conceptual illustration

Structure

A second call judges the first call's work

Source: Anthropic, "Building Effective Agents", "Workflow: Evaluator-optimizer". Statuses from the cookbook notebook evaluator_optimizer.ipynb.

On entering: four places, all empty.

Step 1: the task goes to the generator. One model call writes a response.

Step 2: a second call, the evaluator, judges that response and writes feedback. In the notebook the evaluator has its own prompt and its own list of criteria.

Step 3: if the verdict is not PASS, the feedback goes back to the generator, and the generator tries again.

Step 4: when the evaluator returns PASS, the loop ends and the result is returned. The article compares this to the drafting and revising a human writer does to produce a polished document.

Conceptual illustration

What goes back

Each retry is sent every earlier attempt and the latest feedback

Source: Anthropic cookbook notebook evaluator_optimizer.ipynb, the loop(), generate() and evaluate() functions.

On entering: three generation calls, not yet filled in. This slide reads the notebook's code and draws what each call receives.

Step 1: the first call is sent the generator prompt and the task.

Step 2: the second call is sent the prompt, the first attempt, the evaluator's feedback on it, and the task.

Step 3: the third call is sent both earlier attempts and the feedback on the second one. The feedback on the first attempt is not sent again.

Step 4: so the generator's input grows by one attempt per round. The evaluator's does not: it is sent the task and the current attempt only.

What the feedback changed

The second draft answers each area of the feedback

Source: evaluator_optimizer.ipynb, saved output. Feedback is paraphrased. Matching it to the second draft is this deck's reading of that output.

On entering: the evaluator's four areas, with the number of points under each.

Step 1: error handling. The second draft raises IndexError from pop and getMin on an empty stack.

Step 2: type hints. The two lists are now typed. The evaluator also asked for a return type hint on pop, which the first draft already had.

Step 3: documentation. The class and every method have docstrings, and push describes its argument.

Step 4: edge cases. push now raises TypeError when it is given something that is not an integer.

Step 5: the limit of this evidence. Every area shows a matching change, but no second evaluation is saved. One thing a second evaluator might raise: the new docstring for pop says it removes and returns the top element, while the function returns nothing. That observation is mine, from reading the saved code.

Part two

What it costs

Every round is two more model calls

The sources do not list failure modes for this workflow. They do state the cost of systems like it, and the notebook's code shows when the loop stops. This part stays with those two things.

Computed

Calls per round

Each round of feedback adds two model calls

Source: Anthropic, "Building Effective Agents", "When (and when not) to use agents". Loop from evaluator_optimizer.ipynb. Calls computed as 2 × rounds.

On entering: four possible runs, by the evaluation on which the response passes.

Step 1: a pass on the first evaluation takes two calls: one generation, one evaluation. Each extra round adds two more. Four rounds is eight calls.

Step 2: the article states the trade in general terms: these systems give up latency and cost to get better task performance, and you should decide whether that trade makes sense.

Step 3: the notebook's loop is written as a loop with no round limit. It returns only when the evaluator says PASS, and its evaluator is told to pass only when every criterion is met and it has nothing more to suggest. The notebook is a minimal example. The number of rounds in a real run is not something these sources measure.

Part three

When to use it

Clear criteria, and feedback that makes the result better

The article gives two signs of a good fit and two examples. Then the pair to tell apart, and a checklist.

Conceptual illustration

The decision

Two signs say the loop will pay off

Source: Anthropic, "Building Effective Agents", "Workflow: Evaluator-optimizer". Reflection as described in this set's Reflection deck.

On entering: two signs, both from the article.

Step 1: the first sign: responses get demonstrably better when a person states their feedback.

Step 2: the second sign: the model can give that kind of feedback itself.

Step 3: the article's two examples. Literary translation, where a first draft can miss nuances that an evaluator can point out. Complex search, where the evaluator decides whether more searching is needed.

Step 4: the pair to tell apart. Here a separate call does the evaluating, with its own prompt and criteria. In Reflection, as the earlier deck in this set describes it, the model grades its own output against a rubric. The article does not make this comparison. It is this set's.

Conceptual illustration

Checklist

Six checks before you add an evaluator loop

Source: Anthropic, "Building Effective Agents", "Workflow: Evaluator-optimizer" and "When (and when not) to use agents".

Steps 1 to 4: the conditions the article and the notebook give for a good fit: clear criteria, measurable value from refinement, and the two signs.

Steps 5 and 6: the article's general advice. Find the simplest solution that works, and add a loop like this only when the gain is worth the extra latency and cost. For many applications one well-tuned call is enough.

Takeaway

A second call can make the first one better. Use it when the criteria are clear and the extra calls are worth it.

What would change this advice: criteria nobody can state, or output that feedback does not improve. Then the loop only adds calls. This is the last workflow pattern. The loop family comes next, starting with "Measure, change one thing".
