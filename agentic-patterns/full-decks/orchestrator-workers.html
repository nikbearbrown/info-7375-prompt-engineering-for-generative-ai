Agentic patterns · Workflow

Orchestrator-workers

One model decides the subtasks. Other model calls do them.

This deck covers one pattern: orchestrator-workers. It shows the shape of the pattern, what it costs and where it can go wrong, and the questions that decide whether to use it.

Conceptual illustration

Where this pattern sits

Twenty patterns in three families

Sources: Design of Agentic Systems with Case Studies, Chapter 3. Anthropic, "Building Effective Agents". The Forward Future Loop Library (85 loops).

On entering: an empty map. The set of decks covers twenty patterns, grouped by the question each family answers.

Step 1: reasoning patterns. These describe how one agent orders its own thinking and tool calls.

Step 2: workflow patterns. These describe how several model calls are wired together.

Step 3: loop patterns. These are grouped by the check that keeps a long run honest.

Step 4: this deck is orchestrator-workers, the fourth workflow pattern.

The claim

The orchestrator chooses the subtasks after it reads the task. That makes the workflow flexible, and every subtask is one more model call.

Both halves come from the same design. Nobody lists the subtasks in code, so the workflow can fit an input nobody predicted. The price is a planning call before any work starts, and then one call for each subtask the orchestrator writes.

Structure

The subtasks are written after the task arrives

Source: Anthropic, "Building Effective Agents", "Workflow: Orchestrator-workers".

On entering: four moments, left to right. The third column is empty on purpose. Nobody has listed the subtasks.

Step 1: a task arrives and a central model, the orchestrator, reads it.

Step 2: the orchestrator breaks the task down. How many subtasks there are, and what they are, depends on this input.

Step 3: each subtask goes to a worker, which is another model call.

Step 4: the results come back and the orchestrator combines them into one answer. The article describes all four moments. The cookbook notebook on the next slides stops after the third: it returns the workers' results and lists a combining step as a next step.

Conceptual illustration

How it works

The orchestrator's output becomes each worker's prompt

Source: Anthropic cookbook, orchestrator_workers.ipynb, "How It Works" and "Implementation".

On entering: the notebook splits the pattern into two phases.

Step 1: analysis and planning. The orchestrator receives the task and its context.

Step 2: it returns an analysis and a list of subtasks in XML. Each subtask has a type and a description. The words between the tags here are placeholders.

Step 3: execution. Each worker receives three things: the original task, its own subtask type and description, and any additional context.

Step 4: the worker returns its content inside a response tag. The notebook gives workers the original task as well as their own instructions, so each one has the full context.

What it costs

N + 1 model calls, and three places the hand-off can go wrong

Both slides in this part come from the notebook's own section on limitations.

Computed

Cost and latency

Three subtasks mean four model calls

Source: orchestrator_workers.ipynb, "Limitations & Considerations". Counts computed as N + 1 with N = 3. Equal call times are an assumption.

On entering: one assumption for this picture: every model call takes the same time, one unit. Real calls vary.

Step 1: a single call. One call, one unit of waiting.

Step 2: orchestrator-workers with three subtasks, the way the notebook runs it. The workers run one at a time, so four calls take four units.

Step 3: the notebook suggests running the workers in parallel. Still four calls. The wait drops to two units: the orchestrator, then the slowest worker.

Step 4: the count is always one orchestrator plus N workers. Parallel workers cut the wait and leave the number of calls alone. The article's general advice applies here: these systems often trade latency and cost for better task performance, so check that the trade is worth it.

Failure modes

The hand-off can go wrong in three places

Source: orchestrator_workers.ipynb, "Limitations & Considerations" and "Next Steps".

On entering: the notebook's pipeline: the orchestrator's answer is parsed, the workers run, the results are returned.

Step 1: the orchestrator might not break the task down well.

Step 2: parsing can fail if the model does not follow the XML format exactly.

Step 3: a worker may return an empty or malformed response.

Step 4: what the notebook says about each. Prompt engineering is critical for the breakdown. JSON is worth considering in place of XML. Empty worker responses are caught by validation and replaced with an error marker. The notebook has no retry and no combining step; it lists both as next steps. These are failure modes the notebook names, not rates anyone measured.

Part three

When to use it

Complex tasks whose subtasks you can't list in advance

The article's two examples: coding products that change several files, where the files and the changes depend on the task, and search tasks that gather and analyze information from several sources. Its wider advice is to look for the simplest solution first and add complexity only when it is needed.

Conceptual illustration

The decision

Three questions decide whether orchestrator-workers fits

Source: orchestrator_workers.ipynb, "When to use this workflow". Anthropic, "Building Effective Agents", "Workflow: Orchestrator-workers".

On entering: three questions, asked in order.

Step 1: does the task need several distinct approaches? If it has one clear output, a single model call is enough and the workflow is unnecessary complexity.

Step 2: can you list the subtasks in advance? If they are always the same, use parallelization. If they depend on the input, this is the pattern.

Step 3: is latency critical? Several model calls add overhead.

Step 4: the pair to tell apart. Both send work to several model calls. In orchestrator-workers the orchestrator chooses the subtasks from the input. In parallelization the subtasks are fixed in advance. Both sources draw this line.

Takeaway

Use orchestrator-workers when the input decides the subtasks. If you can list them in advance, use something simpler.

What would change this advice: a task whose subtasks turn out to be the same every time. Then the planning call is wasted and parallelization does the job. Next in the set: evaluator-optimizer, where one model call writes and another gives feedback in a loop.
