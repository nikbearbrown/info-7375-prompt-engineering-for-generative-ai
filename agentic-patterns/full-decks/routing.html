Agentic patterns · Workflow

Routing

Classify the input. Send it to the path built for it.

This deck covers one workflow pattern: routing. It shows the shape of the pattern, what it costs, and the questions that decide whether to use it.

Conceptual illustration

Where this pattern sits

Twenty patterns in three families

Sources: Design of Agentic Systems with Case Studies, Chapter 3. Anthropic, "Building Effective Agents". The Forward Future Loop Library (85 loops).

On entering: an empty map. The set of decks covers twenty patterns, grouped by the question each family answers.

Step 1: reasoning patterns. These describe how one agent orders its own thinking and tool calls.

Step 2: workflow patterns. These describe how several model calls are wired together.

Step 3: loop patterns. These are grouped by the check that keeps a long run honest.

Step 4: this deck is Routing, the second workflow pattern.

The claim

Routing sends each kind of input to a prompt built for it. Everything then rests on the classification.

Both halves come from one step. A classifier in front decides which path an input takes. That lets each path specialise. It also means the paths can only be as good as the label they are handed.

Part one

The shape

Classify first, then hand off to a specialised path

Three slides: the structure, a worked example with three support tickets, and why separate paths help.

Conceptual illustration

Structure

A router classifies the input and one path handles it

Source: Anthropic, "Building Effective Agents", "Workflow: Routing".

On entering: the parts, not yet active.

Step 1: one input arrives. The router's only job is to classify it.

Step 2: behind the router sit several paths. Each can have its own prompt, its own tools, even its own model.

Step 3: the router picks one path and that path handles the input. The other paths are not used.

Step 4: the router does not have to be a model call. The article says the classification can be done by a model or by a traditional classification model or algorithm.

Three support tickets, each sent to a different team's prompt

Source: Anthropic cookbook notebook basic_workflows.ipynb, example 3. Routes are the notebook's recorded output; counts are tallied in code.

On entering: three support tickets and four available routes: billing, technical, account and product. The article's first example of routing is the same idea: customer service queries of different types go to different processes, prompts and tools.

Step 1: ticket 1 is a login problem. The router selects account.

Step 2: ticket 2 is an unexpected charge. The router selects billing.

Step 3: ticket 3 asks how to export data. The router selects technical.

Step 4: three tickets, three different routes. The product route was not selected. Ticket 3 is a how-to question, and the router chose technical over product. That choice is the router's judgment. Hold on to it for part two.

Conceptual illustration

Why it helps

One prompt for every input has to pull in several directions

Source: Anthropic, "Building Effective Agents", "Workflow: Routing". Prompt guidelines condensed from the cookbook notebook basic_workflows.ipynb.

On entering: suppose one prompt has to handle every ticket.

Step 1: it needs everything the four teams need: explain charges in a friendly tone, give exact technical steps, put account security first in a serious tone, teach product features in an encouraging tone.

Step 2: some of those pull against each other. The article's point: without routing, optimizing for one kind of input can hurt performance on the others.

Step 3: with routing, each route has its own prompt.

Step 4: the article calls this separation of concerns. In the notebook's code only the selected prompt is sent with the ticket, so the other prompts are never read for that input.

Part two

What it costs

One more step in front of every input, and nothing behind it to catch a wrong label

The article does not describe a failure mode for routing. It states a condition: the classification has to be accurate. These two slides show the cost of the extra step and why that condition matters.

Computed

The extra step

Routing puts one more call in front of every answer

Source: Anthropic cookbook notebook basic_workflows.ipynb, the route function. "Building Effective Agents", "Workflow: Routing". Counts computed in code.

On entering: the same three tickets.

Step 1: with one prompt and no router, each ticket is one model call. Three calls.

Step 2: the notebook's route function makes two calls per ticket: one to select the route, one to answer with the selected prompt. Six calls.

Step 3: the notebook says these workflows trade cost or latency for potentially better task performance. The router here is a model call that explains its reasoning and then names a route. The article allows a traditional classifier in its place.

Step 4: routing can also save money. The article's second example routes by difficulty: easy or common questions go to a smaller, cost-efficient model, and hard or unusual ones go to a more capable model.

Why accuracy matters

Nothing after the router checks its choice

Source: Anthropic cookbook notebook basic_workflows.ipynb, the route function. Anthropic, "Building Effective Agents", "Workflow: Routing".

On entering: ticket 2, the unexpected charge, and three things the router could say about it.

Step 1: the router says billing. The code looks up the billing prompt and the billing reply comes back. This is what the notebook recorded.

Step 2: suppose the router says technical. The code looks up the technical prompt in exactly the same way. A technical reply comes back, and no error is raised.

Step 3: suppose the router names a team that is not in the list. The lookup fails with a KeyError and the run stops.

Step 4: the selected prompt answers whatever it is given. That is why the article's condition for routing is that classification can be handled accurately. Rows 2 and 3 come from reading the notebook's code. I did not run them, and the article does not describe them.

Part three

When to use it

Distinct kinds of input, and a classifier you can trust

Two questions, the pair to tell apart, and a checklist.

Conceptual illustration

The decision

Two questions decide whether routing fits

Source: Anthropic, "Building Effective Agents", "Workflow: Routing", "What are agents?" and "When (and when not) to use agents".

On entering: two questions, asked in order.

Step 1: are there distinct kinds of input that are better handled separately? If not, the article's general advice applies: a single call with retrieval and good examples is usually enough.

Step 2: can the classification be done accurately, by a model or by a traditional classifier? The article gives this as a condition for routing to work well.

Step 3: the pair to tell apart. Routing is a workflow: in the article's words, the model and tools follow "predefined code paths", and the model only picks which one runs. In an agent the model directs its own process and its own tool use.

Step 4: the article's standing advice: find the simplest solution and add complexity only when it is needed.

Conceptual illustration

Checklist

Six checks before you add a router

Source: Anthropic, "Building Effective Agents", "Workflow: Routing" and "When (and when not) to use agents".

Steps 1 to 3: the conditions under which the article says routing works well, plus its second use, routing by difficulty.

Steps 4 to 6: reasons to think again. The article does not call these failures. They follow from its condition on accuracy and from its advice to keep things simple and to weigh cost and latency against the gain.

Takeaway

Routing gives each kind of input its own prompt. It is only as good as the label in front.

What would change this advice: inputs that do not fall into clear kinds, or a classifier you cannot trust. Next in the set: Parallelization, which runs several calls at once and combines their outputs.
