Change with proof

Ground it, make the smallest change, attach the proof.

This deck covers one loop pattern: change with proof. It is for one change that has to be correct. The deck shows the shape, the four loops that share it, the way it fails, and how to tell it from its neighbours.

Where this pattern sits

Twenty patterns in three families

Sources: Design of Agentic Systems with Case Studies, Chapter 3. Anthropic, "Building Effective Agents". The Forward Future Loop Library (85 loops).

On entering: an empty map. The set of decks covers twenty patterns, grouped by the question each family answers.

Step 1: reasoning patterns. These describe how one agent orders its own thinking and tool calls.

Step 2: workflow patterns. These describe how several model calls are wired together.

Step 3: loop patterns. These are grouped by the check that keeps a long run honest.

Step 4: this deck is Change with proof, the third loop pattern.

The claim

When one change must be correct, it is handed over with proof. The agent saying so is not proof.

A loop is a prompt plus a real check plus a stop rule. In this pattern the check is the proof that comes with the change.

Two cautions about the whole loop family. The grouping of the 85 loops into ten patterns is a judgment made from reading the loops. And none of these patterns has been tested here on real agent runs. Treat the deck as a reading of the catalog, not as a result.

Part one

The shape

Structure

Ground it, make the smallest change, attach proof

Source: the loop tree, pattern 3. Loops from the Forward Future Loop Library.

On entering: the problem. There is one change, it has to be correct, and the risk is that the agent guesses.

Step 1: ground it. Read the current code, APIs and tests. For a bug, reproduce the failure first.

Step 2: make the smallest change. The child loops say this as a minimal patch, one small slice, or one code area.

Step 3: attach proof, matched to the kind of change.

Step 4: a loop is a prompt plus a real check plus a stop rule. Here the real check is the proof: a reproduction or a test.

The children

Four loops share this shape

On entering: an empty table. Each loop sits under the pattern its check belongs to.

Step 1: turn a report into a patch. Loop 016 takes a vague ticket and ends with a minimal patch and proof.

Step 2: one feature slice. Loop 068 grounds a small slice in current code, APIs, data contracts and tests before building it. Its cost: it is slower per feature, one slice at a time, with approval before the next.

Step 3: refactor without changing contracts. Loop 069 keeps contracts and tests fixed; it needs a good baseline test suite, and any signature change needs authorization. Loop 002 refactors in steps with a live test and an independent review after each.

Conceptual illustration

Loop 016, the ticket-to-PR-ready loop

A vague ticket becomes a small patch with evidence

Source: loop 016, the ticket-to-PR-ready loop. Loops from the Forward Future Loop Library.

On entering: a vague ticket or a complaint.

Step 1: reproduce the failure.

Step 2: prove the root cause.

Step 3: make a minimal patch.

Step 4: hand over proof. The reviewer gets evidence matched to the failure type: a screenshot, a test, a log or a benchmark. That is why a loose bug report becomes a change that is fast to review.

Step 5: the limits. The loop needs a reproducible failure. And some tickets are not bugs; they need a human decision first.

Part three

How it fails

The proof is only that the agent said so

The pattern needs a way to reproduce or test. Without one there is nothing to check, and a claim takes the place of the proof.

Conceptual illustration

The failure

A claim that it works gives the reviewer nothing to run

Source: the loop tree, pattern 3, "Needs" and "Fails when". The two handovers are illustrative.

On entering: two ways to hand over the same change.

Step 1: the first handover is the change and a sentence saying it works.

Step 2: the reviewer has nothing to run again. The proof is only that the agent said so.

Step 3: the second handover carries the failure, reproduced, and the same check passing after the change. The reviewer can run both.

Step 4: the pattern needs a way to reproduce or test. It fails when the proof is only that the agent said so. The wording of the two handovers is an illustration, not a quoted case.

Part four

When to use it

Pick the pattern from the problem you have

The tree is used top down: first the pattern, from the problem, then the child closest to your subject.

Conceptual illustration

The decision

Pick the pattern from the problem, then the closest child

Source: the loop tree, patterns 1 to 3 and "How to use the tree". Loops from the Forward Future Loop Library.

On entering: three problems that can look alike.

Step 1: each problem points to a different pattern. One change that must be correct points here.

Step 2: then pick the child closest to your subject: a report, a feature slice, or a refactor. If none fits, write your own child. Keep the pattern's shape and supply your own check.

Step 3: the pair to tell apart. Change with proof is one change, and the check is proof for that change. Burn down a worklist is many small fixes, and the check is the same scan, run again.

Conceptual illustration

Checklist

Six checks before you run a change-with-proof loop

Source: the loop tree, pattern 3, and loops 016, 068 and 002. Loops from the Forward Future Loop Library.

Steps 1 to 3: the conditions the pattern asks for: one change that must be correct, a way to reproduce or test, and a change that can stay small.

Steps 4 to 6: where it breaks. The first is the pattern's own failure. The second is from loop 016: some tickets are not bugs. The third is from loop 002: "until you are happy" is a subjective stop, so define what satisfactory means first, or the loop can run indefinitely.

Takeaway

Ground it, change as little as possible, attach the proof. If the only proof is that the agent said so, it is not done.

What would change this advice: real runs. This pattern is a reading of the catalog and has not been tested here. Next in the set: Maker is not the checker, where a different session or model reviews the work.
