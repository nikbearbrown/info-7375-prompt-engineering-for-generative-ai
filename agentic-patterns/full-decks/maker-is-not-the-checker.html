Maker is not the checker

One agent builds. A different one reviews.

This deck covers one loop pattern: the agent that builds the work is not the one that reviews it. It shows the shape of the loop, the six loops in the library that use it, the ways it fails, and when to pick it.

Conceptual illustration

Where this pattern sits

Twenty patterns in three families

Sources: Design of Agentic Systems with Case Studies, Chapter 3. Anthropic, "Building Effective Agents". The Forward Future Loop Library (85 loops).

On entering: an empty map. The set of decks covers twenty patterns, grouped by the question each family answers.

Step 1: reasoning patterns. These describe how one agent orders its own thinking and tool calls.

Step 2: workflow patterns. These describe how several model calls are wired together.

Step 3: loop patterns. These are grouped by the check that keeps a long run honest.

Step 4: this deck is Maker is not the checker, the fourth loop pattern.

The claim

A model grading its own work shares its own blind spots. Give the review to a different reviewer, and keep the bar fixed.

A loop is a prompt plus a real check plus a stop rule. In this pattern the check is a review by someone other than the maker.

Say this plainly: the loops come from a public library of submitted ideas. Grouping them into ten patterns is a judgment made from reading them. None of it has been tested on real agent runs, and the library shows no run results. Treat the claim as the pattern's stated problem, not as a measured finding.

Part one

The shape

One agent builds, a different one reviews, against fixed criteria

Two slides: the problem the pattern answers, then the loop itself.

Conceptual illustration

The problem

A model grading its own work shares its own blind spots

Source: the loop tree, pattern 4. Loops from the Forward Future Loop Library.

On entering: the maker has built some work, and the work has one flaw in it.

Step 1: the maker did not see the flaw. Call the part it does not see its blind spot.

Step 2: the same model reviews its own work. It has the same blind spot, so the work passes.

Step 3: a different reviewer, another session or another model, looks at the same work. Its blind spot is somewhere else, so the flaw is reported.

Step 4: the flaw never changed. Only the reviewer did. This is the pattern's stated problem drawn as a picture. It is not a measurement.

Conceptual illustration

Structure

The builder fixes what the reviewer finds, until the bar is met

Source: the loop tree, pattern 4. Loops from the Forward Future Loop Library.

On entering: two roles, not yet doing anything.

Step 1: one agent builds the work and hands it over.

Step 2: a different session or model reviews it against criteria that were fixed before the loop started.

Step 3: the findings go back to the builder, who fixes them. Then the reviewer looks again.

Step 4: the loop stops when the reviewer's bar is met. Read it as the three parts of any loop: the prompt is the build, the check is the independent review, and the stop rule is the reviewer's bar.

Part two

The loops

Six loops, four ways to keep the maker and the checker apart

The library has six loops with this shape. They differ in how the reviewer is made independent.

Conceptual illustration

The six loops

Six loops keep the two apart in four ways

Source: the loop tree, pattern 4. Loops from the Forward Future Loop Library.

On entering: four ways to make the reviewer independent.

Step 1: two different model vendors. In 019, Claude builds and Codex reviews. In 034, two models from different providers take turns until both approve the same version.

Step 2: separate sessions or worktrees. In 020, output ships only after a second session verifies it. In 027, a builder and a reviewer pass a baton between worktrees, and each new test must prove it can catch the bug it fixes.

Step 3: a critic attacks a design. In 024, every objection is tracked and none closes without evidence.

Step 4: a fresh independent re-score. In 075, the lowest score gets fixed, then a fresh reviewer scores again.

Illustrative data

One loop, walked through

019: a second vendor reviews until no blocking finding is left

Source: loop 019, The Clodex adversarial-review loop, Forward Future Loop Library. The finding counts are illustrative.

On entering: the columns. Claude is the builder, Codex is the reviewer. The finding counts on this slide are made up to show the mechanism.

Step 1: round one. Claude builds a change and opens a pull request. Codex reviews it and returns two blocking findings and three minor ones.

Step 2: round two. Claude fixes the blocking findings. Codex reviews again and finds one more.

Step 3: round three. No blocking finding is left, so the bar is met and the loop stops.

Step 4: two things to notice. Minor findings are still open, because the severity threshold is a ceiling on what is acceptable, not a promise that everything was fixed. And every round costs two model passes, so the loop uses double the tokens. It also needs both Claude and Codex and the Clodex tool.

Part three

How it fails

The reviewer is not independent, or the bar moves

The pattern needs one thing, a reviewer who is really independent. Both failures come from losing that, or from changing what the reviewer is asked to hold.

Conceptual illustration

Needs and failures

Two prompts to one model is still one model

Source: the loop tree, pattern 4, "Needs" and "Fails when". Cautions from the entries for loops 034 and 075.

On entering: what the pattern needs: a genuinely independent reviewer.

Step 1: the first failure. Builder and reviewer are the same model with different prompts. The roles have different names, but the reviewer is not independent.

Step 2: the second failure. The bar gets lowered to finish. The loop stops because the bar moved, not because the work passed. The example bar is illustrative.

Step 3: two more cautions. Agreement between two models is not truth. And if every score has to be perfect, the loop may never stop. Both cautions are a reading of the loop entries, not statements from the library itself.

Part four

When to use it

When the risk is a model approving its own work

Pick a pattern from the problem you have, then the loop closest to your subject.

Conceptual illustration

The decision

Pick the pattern from the problem, then the loop from the subject

Source: the loop tree, "How to use the tree", and the loop entries. The contrast with Reflection is this set's.

On entering: start from the problem, not from the loop.

Step 1: if the problem is that a model would be grading its own work, this is the pattern.

Step 2: then pick the loop closest to your subject: a change or a plan, repo chores with no one watching, long coding runs where fake tests are the risk, a design before you build, or polish where good is subjective.

Step 3: if none fits, write your own. Keep the shape and supply your own check. A new loop is worth keeping only if it adds a check or a subject the pattern does not already cover.

Step 4: the pair to tell apart. Here a separate session or model reviews the work. In Reflection, from the reasoning family, the same model evaluates its own output against a rubric. That contrast is made by this set of decks. The loop tree does not mention Reflection.

Checklist

Seven checks before you run a maker-checker loop

Source: the loop tree, pattern 4, and the entry for loop 034. Loops from the Forward Future Loop Library.

Steps 1 to 4: what has to be true before the loop starts: the problem is self-grading, the reviewer is separate, the criteria are fixed, and there is a stop rule.

Steps 5 to 7: the ways it fails. If any of these describes your setup, the review is not doing its job.

Takeaway

A review counts only when the reviewer is not the maker. Keep the two apart and keep the bar fixed.

The loop tree rates this among its stronger patterns, and says that is a judgment from reading, not from running the loops. What would change the advice: evidence from real runs that a separate reviewer does or does not catch more.
