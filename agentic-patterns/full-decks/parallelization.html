Parallelization

Run the calls at once. Combine the outputs in code.

This deck covers one workflow pattern: parallelization. It shows the shape and its two variations, what the pattern costs, and the questions that decide whether to use it.

The claim

Parallelization runs several model calls at once and combines their outputs in code. It shortens the wait. It does not reduce the number of calls.

The first sentence is the article's definition. The second is the trade this deck works through: the calls overlap in time, but each one is still made and still paid for.

Part one

The shape

Fan out, then gather. Two variations: sectioning and voting

Three slides: the basic shape, the two variations the article names, and the cookbook notebook's worked example.

Conceptual illustration

Structure

Several calls run at once, and code combines the results

Source: Anthropic, "Building Effective Agents", "Workflow: Parallelization" and "What are agents?".

On entering: one input, three model calls and a combine step, all waiting.

Step 1: the input goes to all three calls and they start at the same moment. No call waits for another.

Step 2: each call returns its own output.

Step 3: the outputs are combined programmatically. In the basic shape the combining is done by code, not by another model.

Step 4: the path is written in code before any input arrives. The article calls that a workflow. In an agent, the model itself decides its process and tool use.

Conceptual illustration

Two variations

Sectioning splits the task. Voting repeats it.

Source: Anthropic, "Building Effective Agents", "Workflow: Parallelization". Examples paraphrased from the article.

On entering: the two names.

Step 1: sectioning breaks one task into independent subtasks. Each call does a different piece, and code joins the pieces.

Step 2: voting runs the same task several times to get diverse outputs, and code counts them.

Step 3: the article's examples. Sectioning: one call answers the user while a second screens the request, and automated evaluations where each call grades one aspect. Voting: several prompts reviewing the same code for vulnerabilities, and several prompts judging whether content is inappropriate.

Part two

What it costs

The wait gets shorter. Every call is still made

The article's Parallelization section names no failure mode, so this part is about cost. Its general advice is that agentic systems trade latency and cost for task performance, and that the trade has to be weighed.

Illustrative data

Wait against calls

Four calls at once: one call's wait, four calls' bill

Source: Anthropic, "Building Effective Agents", "When (and when not) to use agents". The 6 s per call is illustrative; totals are computed in code.

On entering: four calls. The 6 seconds per call is an illustrative input, stated on the slide.

Step 1: one at a time, the wait is 4 times 6, which is 24 seconds.

Step 2: with three workers, the notebook's default, three calls run together and the fourth follows: 12 seconds.

Step 3: with four workers every call runs at once: 6 seconds, the time of one call.

Step 4: the number of calls is four in every row. Running calls together changes the wait and leaves the count alone.

Illustrative data

Voting

With voting, the threshold decides, and every vote is a call

Source: Anthropic, "Building Effective Agents", "Workflow: Parallelization". The five votes are illustrative; each decision is computed in code.

On entering: one question asked five times. This follows the article's content-review example.

Step 1: five calls return at once. In this illustration three say flag and two say pass.

Step 2: three thresholds applied to the same five votes. At least one flag: flagged. At least three: flagged. All five: passed.

Step 3: the article's point is that different vote thresholds balance false positives against false negatives. The price is plain: five votes are five calls for one decision.

Part three

When to use it

Independent pieces, or a decision worth several opinions

Three questions, the pair to tell apart, and a checklist.

Conceptual illustration

The decision

Three questions decide whether to run calls in parallel

Source: Anthropic, "Building Effective Agents", "Workflow: Parallelization", "Workflow: Prompt chaining" and "Workflow: Orchestrator-workers".

On entering: three questions.

Step 1: do the pieces need each other's output? If not, they can be sectioned. If each step works on the previous step's output, that is prompt chaining.

Step 2: would several attempts or viewpoints raise confidence? If yes, voting. If not, the article notes that for many applications one well-tuned call is enough.

Step 3: are the subtasks known in advance? If yes, parallelization. If they depend on the input, orchestrator-workers.

Step 4: the pair to tell apart. The article says the two are structurally similar. The difference is who chooses the subtasks: code, ahead of time, or a central model, from each input.

Takeaway

Parallelization shortens the wait, not the bill. Use it for independent pieces, or when a second opinion is worth a second call.

What would change this advice: if the subtasks can't be listed before the input arrives, the fixed fan-out no longer fits. Next in the set: Orchestrator-workers, where a central model decides the subtasks at run time.
