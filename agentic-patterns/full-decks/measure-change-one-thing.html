Measure, change one thing

Keep a change only if the number got better.

This deck covers one loop pattern. Its full name in the loop tree is "Measure, change one thing, keep it only if better". The deck shows the shape of the loop, the eleven loops that share it, the way it fails, and how to choose it.

Conceptual illustration

Where this pattern sits

Twenty patterns in three families

Sources: Design of Agentic Systems with Case Studies, Chapter 3. Anthropic, "Building Effective Agents". The Forward Future Loop Library (85 loops).

On entering: an empty map. The set of decks covers twenty patterns, grouped by the question each family answers.

Step 1: reasoning patterns. These describe how one agent orders its own thinking and tool calls.

Step 2: workflow patterns. These describe how several model calls are wired together.

Step 3: loop patterns. These are grouped by the check that keeps a long run honest.

Step 4: this deck is Measure, change one thing, the first loop pattern.

The claim

A change stays only when the same measurement says it helped and nothing else got worse.

A loop is a prompt plus a real check plus a stop rule. In this pattern the check is a measurement. Two cautions before we start. The grouping of the 85 loops into ten patterns is a judgment made from reading the catalog. And none of it has been tested on real agent runs. Treat what follows as a careful reading, not as a result.

Part one

The shape

Baseline, one change, re-measure, keep or revert

Two slides: the problem this loop is for, and the loop itself with its check and its stop rule marked.

Illustrative data

The problem

The number improved. Something else got worse.

Source: the loop tree, pattern 1 (Problem), and loop 011. Loops from the Forward Future Loop Library. Inputs are illustrative; the 30% is computed in code.

On entering: one change to a test suite: skip the slow integration tests.

Step 1: the number you are watching is runtime. It falls from 240 seconds to 168. That is 30 percent faster. Judged on runtime alone, the change is kept.

Step 2: the number you were not watching is coverage. It fell from 92 percent to 83. The catalog's test-suite speed loop is defined as cutting runtime without cutting coverage, and this is why.

Step 3: this is the problem the pattern is for. You want a number to go the right way, and a change can quietly make something else worse. The answer is a guardrail: a second number the change is not allowed to make worse.

Conceptual illustration

Structure

One change at a time, judged by the same measurement

Source: the loop tree, pattern 1 (Shape). Loops from the Forward Future Loop Library.

On entering: four places, not yet filled in.

Step 1: record a baseline, once, under fixed conditions.

Step 2: make one change. One, so that the next measurement can be blamed on it.

Step 3: measure again, under the same conditions as the baseline.

Step 4: the check. Keep the change only if the metric improved and no guardrail regressed. Otherwise revert it. Then go round again.

Step 5: the stop rule. Repeat until the target is reached or the returns diminish. A loop is a prompt plus a real check plus a stop rule. This slide marks the last two.

The children

Eleven loops share this shape. The measurement differs.

Illustrative data

Loop 011, the test-suite speed loop

Five changes tried. The guardrail rejects the fastest one.

Source: the loop tree, pattern 1, and loop 011. Each change's effect is an illustrative input; runtimes and decisions are computed in code.

On entering: the baseline: 240 seconds and 92 percent coverage, under fixed conditions. The target is 150 seconds. The guardrail is that coverage must not fall.

Step 1: run the tests in parallel. 180 seconds, coverage unchanged. Kept.

Step 2: skip the slow integration tests. 126 seconds, which would beat the target. Coverage falls to 83 percent, so the change is reverted. This is the catalog's warning made concrete: the loop is easy to win by making the tests less realistic.

Step 3: reuse one database fixture. 162 seconds. Kept.

Step 4: a bigger worker pool. It came out slower, so it is reverted.

Step 5: cache the dependency install. 149 seconds, under the 150 second target, and the stop rule ends the loop. The five changes and their effects are invented for this slide. The arithmetic and every keep or revert decision are computed from them.

Part three

How it fails

The benchmark changes between runs, or nothing says stop

The loop needs one thing: a repeatable measurement. The tree names two ways it fails.

Illustrative data

Fails when

It fails when the benchmark moves or nothing says stop

Source: the loop tree, pattern 1 (Needs, Fails when), and loops 003, 011 and 054. Inputs are illustrative; gains and totals are computed in code.

Step 1: the baseline was taken on a busy machine: 240 seconds. After the change, the run happened on an idle machine: 204 seconds. That looks like a 15 percent gain.

Step 2: measure the changed code again on the same busy machine: 238 seconds. The real gain is under 1 percent. The other 14 points were the machine. Runs under different conditions are not comparable, which is why the loop needs a repeatable measurement.

Step 3: the second failure. Suppose the first kept change saves 40 seconds and each later one saves half as much. The target is 150 seconds.

Step 4: the gains add up to at most 80 seconds, so the number approaches 160 and never reaches 150. Without a stop rule the loop keeps spending. A rule that stops when a kept change improves the number by less than 2 percent would have ended it after change 5.

Part four

When to use it

When the problem is a number, and you can measure it the same way twice

How to pick this pattern out of the ten, and a checklist before you start.

Conceptual illustration

The decision

Pick the pattern by its check, then the loop by your subject

Source: the loop tree, "How I built the tree", "How to use the tree", and patterns 1 and 2. Loops from the Forward Future Loop Library.

On entering: the tree groups loops by what the check is, because the check is what makes a loop reliable.

Step 1: the tree names five kinds of check: a measurement, a scan, an independent reviewer, a ledger and a clean replay. If your check is a measurement, you are in this pattern. Matching each check to a pattern name is my reading of the tree.

Step 2: then pick the child closest to your subject. If none fits, write your own: keep the pattern's shape and supply your own check.

Step 3: the pair to tell apart. Both loops repeat until done. In this pattern a number has to move. In the next one a list of known problems has to get shorter.

Conceptual illustration

Checklist

Six checks before you start the loop

Source: the loop tree, pattern 1 (Problem, Needs, Fails when), and loops 003 and 011. Loops from the Forward Future Loop Library.

Steps 1 to 3: what has to be true before the loop starts: a number to move, a repeatable measurement, and a target or a diminishing-returns rule decided first.

Steps 4 to 6: the ways it breaks. The first two are the tree's own "fails when". The third is the problem from the start of the deck: the number can be won by making something else worse, unless a guardrail is watching.

Takeaway

Name the metric, the guardrails and the stop rule before the first change.

The tree rates this pattern among the strongest, on the condition that the metric is real. That rating is a judgment from reading the loops, not from running them. Next in the set: Burn down a worklist, where the check is a scan and the loop ends when the list is empty.
