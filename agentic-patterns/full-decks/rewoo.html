Agentic patterns · Reasoning

ReWOO

Plan every tool call first. Then run them together.

This deck covers one pattern: ReWOO, short for reasoning without observation. It shows the shape of the pattern, where its speed comes from, the way it fails, and the questions that decide whether to use it.

Conceptual illustration

Where this pattern sits

Twenty patterns in three families

Sources: Design of Agentic Systems with Case Studies, Chapter 3. Anthropic, "Building Effective Agents". The Forward Future Loop Library (85 loops).

On entering: an empty map. The set of decks covers twenty patterns, grouped by the question each family answers.

Step 1: reasoning patterns. These describe how one agent orders its own thinking and tool calls.

Step 2: workflow patterns. These describe how several model calls are wired together.

Step 3: loop patterns. These are grouped by the check that keeps a long run honest.

Step 4: this deck is ReWOO, the third reasoning pattern.

The claim

ReWOO commits to every tool call before any tool has run. That makes it fast, and it means the plan can't change.

Both halves come from one decision. Because no call waits to read a result, the calls can run together. Because no call waits to read a result, nothing a tool returns can alter what runs next.

Part one

The shape

Plan first, run the tools together, then write the answer

Two slides: the three stages, and the latency arithmetic that is the reason to use the pattern.

Conceptual illustration

Structure

The planner writes every tool call before any tool runs

Source: Chapter 3, "ReWOO (Reasoning WithOut Observation)". Pattern from Xu et al., 2023.

On entering: three empty stages. ReWOO separates planning from tool execution entirely.

Step 1: the planner writes the full tool-call sequence. At this point no tool has been invoked, so the planner has seen no result.

Step 2: then all the tools run, in parallel or in batch. The five results arrive together.

Step 3: the answer is written in a synthesis step after execution. Notice what is missing compared with ReAct: no call was chosen after reading a result.

Computed

Why it is fast

Five independent calls finish in the time of the slowest one

Source: Chapter 3, "ReWOO". Both totals are computed in code from 5 calls at 300 ms.

On entering: a time axis and five tool calls of 300 milliseconds each.

Step 1: a ReAct agent runs them one at a time, because each thought waits for the previous observation. Five times 300 is 1,500 milliseconds.

Step 2: ReWOO starts all five at once. The total is the longest single call, 300 milliseconds.

Step 3: that is a five times reduction. The chapter is clear that it only appears when the calls are independent. The next part shows what happens when they are not.

Part two

How it fails

The plan was fixed before any result arrived

Three slides. Dependencies between calls eat the speed gain. A dependent call needs a value the planner never saw. And an unexpected result has nowhere to go.

Illustrative data

Data dependencies

Every call that has to wait gives back part of the gain

Source: Chapter 3, "ReWOO". The dependency chains are a worked example; totals are computed in code.

On entering: the independent case from the last slide. No call waits, the total is 300 milliseconds, and the gain is 5 times.

Step 1: suppose call 2 needs what call 1 returns. It can't start until call 1 finishes. The total is 600 milliseconds and the gain is 2.5 times.

Step 2: call 3 needs call 2. The total is 900 milliseconds, a gain of 1.67 times.

Step 3: call 4 needs call 3. The total is 1,200 milliseconds, a gain of 1.25 times.

Step 4: every call depends on the one before. The total is 1,500 milliseconds, the same as running in sequence. The chapter gives the two end points, 300 and 1,500. The steps in between are this deck's worked example from the same inputs.

Illustrative data

Data dependencies

A dependent call needs a value the planner has not seen

Source: Chapter 3, "ReWOO". Tool names are the chapter's; the argument of call 3 is illustrative.

On entering: a plan of three calls, written before any tool runs.

Step 1: call 3 needs the product, and the product is something call 1 returns. Call 1 has not run.

Step 2: one way out is for the planner to write the call anyway, without the real value. The chapter's words for this: ReWOO degrades its plan quality.

Step 3: the other way is a variable placeholder, which is resolved in a synthesis step after execution. The chapter names these two outcomes and no third one.

Conceptual illustration

The structural failure

An unexpected result can't change the plan

Source: Chapter 3, "ReWOO", structural failure mode.

On entering: a fixed plan of five calls.

Step 1: all five are sent at once.

Step 2: four return what the planner expected. Call 3 returns something that should change the tool strategy.

Step 3: there is no mechanism to course-correct. The plan was committed before any observation arrived, so the other calls already ran as planned. A ReAct agent would have read this result before choosing its next action.

Part three

When to use it

Speed matters, and the calls do not need each other

The chapter's summary row for ReWOO: best for speed-critical, independent parallel calls. Breaks on data dependencies between steps.

Conceptual illustration

The decision

Two questions decide whether ReWOO fits

Source: Chapter 3, "The Decision Framework", question 2 and the summary table.

On entering: two questions, asked in order.

Step 1: must a tool result change what runs next? If yes, you need ReAct, because only ReAct reads each result before acting. If the steps are fixed by the task, a plan-first pattern is safe.

Step 2: does any call need another call's output? If the calls are independent, ReWOO gets its full speed gain. If they are not, Plan-and-Execute runs the steps in order and passes each output to later steps.

Step 3: the pair to tell apart. Both write the plan first. ReWOO runs the tool calls together. Plan-and-Execute runs them one after another.

Conceptual illustration

Checklist

Five checks before you choose ReWOO

Source: Chapter 3, "ReWOO" and "The Decision Framework".

Steps 1 to 3: the conditions under which ReWOO fits. Speed is critical, the calls are independent, and the task is past the five-call range where ReAct is comfortable.

Steps 4 and 5: the conditions under which it breaks. Both are about results that matter to later calls. The chapter gives ReWOO fewer conditions than ReAct, so this list is shorter.

Takeaway

ReWOO is fast because it never waits to look. Use it when the calls do not need each other.

What would change this advice: a design that adds a re-planning step gives up some of the speed to get some of the adaptation back. Next in the set: Reflection, a self-audit layer that sits on top of any of these execution patterns.
